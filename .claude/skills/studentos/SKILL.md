## 1. ลำดับการทำงาน — ห้ามข้าม

```
รับโจทย์ → เก็บสเปคให้ครบ → เสนอแผนสั้น → รอ OK → เขียนโค้ด → ส่งให้ Few build → แก้ error → commit
```

### 1.1 เก็บสเปคให้ครบ (ห้ามเดา)

Few บอกชัดว่าสิ่งที่กิน token มากคือ **"คุณเดาเองว่าจะ test ยังไง จะใช้ library อะไร"**
ก่อนเขียนโค้ดฟีเจอร์ใหม่ ต้องรู้ครบ 5 ข้อนี้ — ข้อไหนไม่รู้ **ให้ถามก่อน**:

1. **หน้าไหน / เข้าจากไหน** — เข้าจากแท็บไหน push จากปุ่มอะไร เป็น sheet หรือ full screen
2. **ข้อมูลมาจากไหน** — model ตัวไหนที่มีอยู่แล้ว หรือต้องสร้าง `@Model` ใหม่ (ถ้าใหม่ → §3)
3. **หน้าตาเป็นยังไง** — ใช้คอมโพเนนต์ที่มีอยู่ (`CardContainer`, `TierBadge`) หรือทำใหม่
4. **Free หรือ Pro-gated**
5. **เสร็จแล้วดูยังไงว่าใช้ได้** — Few จะกดตรงไหนแล้วเห็นอะไร (นี่คือ definition of done)

ถ้าโจทย์คลุมเครือ ให้ถามก่อน — คำถามหนึ่งรอบถูกกว่าเขียนโค้ดผิดสามรอบ

### 1.2 เสนอแผนสั้นก่อนลงมือ — ทุกครั้ง

Few เลือกไว้ว่า **"เสนอแผนสั้นๆ ก่อนลงมือทุกครั้ง"** แผนต้องสั้นจริง (5-10 บรรทัด):

```
จะแก้: <ไฟล์> — <ทำอะไร>
จะเพิ่ม: <ไฟล์ใหม่ ถ้ามี>
กระทบ: <ไฟล์อื่นที่ต้องแก้ตาม>
เสี่ยง: <จุดที่อาจพัง>
เช็คยังไง: <Few ต้องกดอะไรถึงเห็นว่าใช้ได้>
```

แล้ว **หยุดรอ OK** ห้ามลงมือทันที

## 2. กฎความซื่อสัตย์ — สำคัญที่สุดในสกิลนี้

Few ระบุปัญหาตรงๆ ว่า **"แก้แล้วคุณบอกใช้งานได้ แต่มันยังใช้งานไม่ได้"**

### 2.1 ห้ามพูดว่า build ผ่าน

**เราไม่ build เอง** — การทดสอบเป็นความรับผิดชอบของ Few (ตามสกิล `run`)

ดังนั้น **ห้ามเขียนประโยคเหล่านี้เด็ดขาด**: "build ผ่านแล้ว" · "คอมไพล์ได้" · "ทดสอบแล้วใช้งานได้" · "แก้เรียบร้อย ใช้ได้เลย"

### 2.2 ต้องปิดท้ายทุกครั้งที่แก้โค้ด ด้วยบล็อกนี้

```
เช็คแล้ว:
- <สิ่งที่ verify ได้จริง เช่น "grep ยืนยันไม่มีที่อื่นเรียก method นี้">

ยังไม่ได้เช็ค:
- ยังไม่ได้คอมไพล์
- <ข้ออื่นๆ>

รบกวน Few:
1. กด ⌘B ใน Xcode
2. ถ้าแดง — copy error ทั้งก้อนจาก Issue Navigator มาวางได้เลย
3. ถ้าเขียว — กด <ปุ่ม/หน้าจอที่ต้องลอง> แล้วบอกว่าเห็นอะไร
```

Few เลือกไว้ว่าอยากได้ทั้ง "xcodebuild ผ่าน = ขั้นต่ำสุด" และ "บอกชัดๆ ว่าอะไรที่ยังไม่ได้เช็ค" — บล็อกนี้คือสิ่งที่ตอบทั้งสองข้อ

### 2.3 เวลาได้ error กลับมา

- อ่าน error **ทั้งก้อน** ก่อนแก้ อย่าแก้บรรทัดแรกแล้วเดาที่เหลือ
- SwiftUI error "unable to type-check this expression in reasonable time" = ต้อง **แตก body เป็น sub-view ย่อย** ไม่ใช่แก้ syntax
- แก้แล้วส่งกลับพร้อมบล็อก §2.2 อีกรอบ
- ถ้าวนเกิน 2 รอบกับ error เดียวกัน → **หยุด อธิบายว่าติดตรงไหน และถามแทนที่จะเดาต่อ**

## 3. กฎเฉพาะโปรเจกต์นี้ (จุดที่เคยพังมาแล้ว)

Few บอกว่าปัญหาใหญ่คือ **"แก้ฟีเจอร์ A แล้วฟีเจอร์ B พัง"** — เช็คลิสต์นี้กันเรื่องนั้นโดยตรง

### เพิ่ม `@Model` ใหม่ → ต้องทำครบ 3 ที่
1. สร้างไฟล์ใน `Core/Models/`
2. เพิ่มใน `Schema([...])` ที่ `App/PrototypeAppApp.swift` — **ลืม = crash ทันทีที่เปิดแอป** (มี `fatalError` รออยู่)
3. เพิ่มใน `SettingsView.resetAllData()` — เคยลืมกับ Calendar 3 ตัวมาแล้ว

### เปลี่ยน schema ของ model ที่มีอยู่
ลบ/เปลี่ยน type ของ property = ข้อมูลเดิมในเครื่องอ่านไม่ได้ → **crash ตอนเปิดแอป**
ถ้าจำเป็นต้องเปลี่ยน ให้บอก Few ว่า **ต้องลบแอปออกจาก simulator/เครื่องก่อน** แล้วติดตั้งใหม่ — เตือนก่อนเสมอ

### แตะไฟล์ที่คนอื่นใช้ต่อ
ก่อนแก้ signature / ลบ property / เปลี่ยนชื่อ type → `grep` หาที่เรียกใช้ทั้งหมดก่อน แล้วบอก Few ว่ากระทบไฟล์ไหนบ้าง

### ไฟล์ใหญ่
`CalendarView.swift` (687) · `SettingsView.swift` (357) · `DashboardView.swift` (350)
อ่านเฉพาะช่วงบรรทัดที่เกี่ยวข้อง (`Read` + `offset`/`limit`) อย่าอ่านทั้งไฟล์ถ้าไม่จำเป็น

### ไฟล์ใหม่ = เข้า target อัตโนมัติ
Xcode project ใช้ file-system-synchronized groups (objectVersion 77) — **ห้ามแก้ `.pbxproj`** เพื่อเพิ่มไฟล์ แค่สร้างไฟล์ในโฟลเดอร์พอ

### API
Deployment target = **iOS 26.5** ใช้ API ใหม่ได้หมด ไม่ต้องเขียน `if #available` ย้อนหลัง
**ไม่มี dependency ภายนอกเลย** — ห้ามเพิ่ม SPM package โดยไม่ถามก่อน

## 4. UI และดีไซน์

### Design tokens — ห้าม hardcode
สี ระยะห่าง มุมโค้ง ต้องมาจาก `Theme` เท่านั้น (`Theme.Colors.primary`, `Theme.Spacing.lg`, `Theme.Radius.card`)
ต้องการโทเคนใหม่ → เพิ่มใน `Theme.swift` ก่อน แล้วค่อยใช้
คอมโพเนนต์ซ้ำใช้ `CardContainer` และ `TierBadge` ที่มีอยู่

### ภาษา
UI ทั้งหมดเป็น **ภาษาไทย** · วันที่ใช้ `Date+Thai.swift` (พ.ศ.) · คอมเมนต์โค้ดเขียนอังกฤษได้ แต่คุยกับ Few เป็นไทย

### เกณฑ์ตัดสินความสวย
ยังไม่มีไฟล์ดีไซน์เป็นต้นฉบับ — ตัดสินจากภาพจริงที่ Few เห็น + มาตรฐาน Apple HIG (iOS 26)

https://www.figma.com/design/7qTFOazJhInRwMm7viQbGr

อ่านด้วย `get_design_context` (ส่ง `clientLanguages: "swift"`, `clientFrameworks: "swiftui"`) เขียนด้วย `use_figma` (โหลด skill `figma-use` + `figma-swiftui` ก่อนทุกครั้ง)

โครงไฟล์ — **แพลน Starter จำกัด 3 pages** จึงจัดกลุ่มด้วย Section แทน:

ทุกเฟรมเป็น iPhone 16 Pro **402×874** ตอนนี้ยังเปล่า มีแค่ status bar / tab bar จางๆ + label กำกับ

### กฎการตั้งชื่อ

```
Frame:     <ชื่อ struct ใน Swift ตรงตัว>   เช่น DashboardView, CalendarView
           state ต่อท้ายด้วยจุด:            DashboardView.empty · CalendarView.dayDetail
Component: ios/TabBar · Card/Default · Badge/Pro · Button/Primary
Variable:  color/primary · space/lg · radius/card   (ผูกกับ Theme.swift 1:1 แล้ว 19 ตัว)
Section:   ชื่อกลุ่มเป็นภาษาไทยได้
```

กฎเดียวที่ต้องจำ: **ชื่อ frame = ชื่อ struct ใน Swift** ไม่มีข้อยกเว้น
เพิ่ม View ใหม่ในโค้ด → เพิ่มเฟรมชื่อเดียวกันในไฟล์นี้

### ข้อจำกัดที่เจอมาแล้วในไฟล์นี้ (อย่าเสียเวลาซ้ำ)

- **ฟอนต์ `SF Pro` ใช้ไม่ได้** — `listAvailableFontsAsync()` บอกว่ามี แต่ node ที่ใช้จะได้ `hasMissingFont: true` และ width 0
  ใช้ **`Inter`** (Latin, style ชื่อ `Semi Bold` มีเว้นวรรค) และ **`Noto Sans Thai`** (ไทย) แทน
- **SF Symbols ใช้ไม่ได้** เพราะ `figma.util.getSfSymbolCharacter()` ต้องพึ่ง SF Pro — ใช้รูปทรงแทนไปก่อน
- **TEXT ใน auto-layout**: ต้อง `textAutoResize='HEIGHT'` → `layoutSizingHorizontal='FIXED'` → `resize(w, h)` → ค่อย `'FILL'`
  ถ้าตั้ง `'FILL'` เฉยๆ node จะยุบเหลือกว้าง 0 (ตัวอักษรเรียงลงมาทีละตัว)
- **`figma.createPage()` เกิน 3 หน้าจะ error** ทั้งสคริปต์ (atomic — ไม่มีอะไรถูกสร้างเลย)

## 6. ลำดับความสำคัญตอนนี้ (โหมดเตรียมเดโม่)

Few ให้น้ำหนักเท่ากันทั้ง 4 ข้อ:
1. **แอปต้องไม่ crash ตอนเดโม่**
2. **Demo flow เดินได้ตลอด** — onboarding → ใช้งาน → จบ ไม่มีหน้าว่าง/ปุ่มกดไม่ได้
3. **ฟีเจอร์ที่โฆษณาไว้ต้องทำงานจริง** — ไม่มี UI ที่กรอกแล้วข้อมูลหายเงียบๆ
4. **UI สวย ดูมืออาชีพ**

เวลาเสนอทางเลือก ให้จัดลำดับตามนี้ และบอกตรงๆ ถ้างานชิ้นไหนเสี่ยงพังของเดิมมากกว่าคุ้ม
